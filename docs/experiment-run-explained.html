Short Version

The research loop ran many small experiments against the same folktales dataset. Each experiment changed one or two training settings in train.py, trained the model for the same 5-minute budget, measured val_bpb, and kept only changes that improved the score.

What Is A Model?

In this project, a model is not just one file. It is two things working together:

  1. The architecture: the recipe for the model, written in code. This says how many layers it has, how wide each layer is, and how text flows through it.
  2. The parameters: millions of numbers inside that architecture. Training adjusts these numbers so the model gets better at predicting the next token.

train.py defines the architecture and training process. During a run, PyTorch creates the model in memory, fills it with starting numbers, trains those numbers, evaluates the result, prints metrics, and exits.

Important: this script does not currently save a trained model checkpoint. It is an experiment harness for comparing ideas. The result that persists is the score in results.tsv and the code changes that produced better scores.

A simple mental model: 

Architecture = the empty machine design
Parameters   = the knobs inside the machine
Training     = turning those knobs using examples
Evaluation   = checking whether the machine predicts held-back text better

What The Research Agent Did

The agent followed the loop described in program.md:

  1. Pick one idea, such as “try a smaller batch size.”
  2. Edit train.py.
  3. Commit the experiment.
  4. Run uv run train.py > run.log 2>&1.
  5. Read the final score from run.log.
  6. Write the result to results.tsv.
  7. Keep the code change if val_bpb improved.
  8. Revert the code change if val_bpb got worse.

This is why results.tsv contains both keep and discard rows. A discarded experiment is still useful because it tells us which direction did not help.

The Parameters We Adjusted

These are the main knobs changed during the run. Think of them as choices about model size, learning speed, and how aggressively the model is allowed to fit the data.

Parameter Plain-English Meaning Why It Matters Best Direction Found
TOTAL_BATCH_SIZE How many tokens the model studies before each update. Smaller batches mean more frequent updates in the same time budget. Smaller was much better: 2**16 to 2**15.
DEPTH How many transformer layers the model has. More layers give capacity, but each step is slower. Depth 2 beat depth 4, 3, and 1.
ASPECT_RATIO Controls model width. In this code, width is based on depth times this value. Wider layers can learn richer patterns, but slow training. Aspect 128 helped; aspect 192 was too much.
MATRIX_LR Learning rate for the main matrix weights optimized by Muon. Controls how big the main internal weight updates are. 0.03 worked best among tested values.
EMBEDDING_LR Learning rate for token embeddings: the model's learned representation of tokens. Controls how fast the model learns useful meanings for token IDs. 0.8 beat 0.6, 0.9, and 1.0.
UNEMBEDDING_LR Learning rate for the output head that turns internal state into next-token predictions. Controls how quickly the final prediction layer changes. The original 0.004 was best among tested values.
WEIGHT_DECAY A regularization force that discourages weights from growing too freely. Can improve generalization, especially on smaller datasets. 0.3 beat 0.2, 0.1, 0.35, and 0.4.
WARMDOWN_RATIO and FINAL_LR_FRAC How the learning rate tapers down near the end of training. Controls whether training slows down early, late, or not enough. The original taper settings were best among tested variants.

What Happened In The Experiments

The score is val_bpb, or validation bits per byte. Lower is better. It is measured on validation text that was held back from training.

Big Wins

Change Score Interpretation
Baseline 1.842572 Starting point before tuning.
Smaller optimizer batch 1.710647 More frequent updates helped a lot.
Depth 3 1.698088 Shallower was faster and better under the time limit.
Depth 2 1.694426 Even shallower improved again.
Depth 2 plus wider layers 1.675139 Recovered useful capacity while staying fast.
Lower matrix LR on the wide shallow model 1.673504 Main weights needed slightly gentler updates after the architecture changed.
Higher embedding LR 1.669677 Token representations benefited from faster learning.
Higher weight decay 1.666085 Stronger regularization gave the best validation score.

Things That Did Not Help

  • One layer: faster, but not enough capacity. Score worsened to 1.703351.
  • Extra-wide model: more capacity, but too slow or too large for the budget. Score worsened to 1.713592.
  • Matrix LR too low: 0.02 and 0.025 undertrained compared with 0.03.
  • Embedding LR too high: 0.9 and 1.0 overshot the better 0.8 setting.
  • Unembedding LR changes: both higher and lower were worse than the original 0.004.
  • Learning-rate schedule changes: tested warmdown changes were worse than the original schedule.

How These Changes Affected The Model

1. The model learned from more feedback

Reducing TOTAL_BATCH_SIZE meant the optimizer updated the model more often. Under a short 5-minute budget, more update chances mattered.

2. The model became shallower and faster

Reducing DEPTH made each training step cheaper. The model had less stacked reasoning depth, but it could process more tokens and take more optimizer steps. For this task and time budget, depth 2 was the best tradeoff.

3. The model got width back after losing depth

Increasing ASPECT_RATIO made the two-layer model wider. That gave each layer more room to represent patterns while keeping the model shallow enough to train quickly.

4. Different parts of the model needed different learning speeds

The main matrix weights preferred MATRIX_LR=0.03. Token embeddings preferred a faster EMBEDDING_LR=0.8. The output head preferred staying at UNEMBEDDING_LR=0.004. These are different sets of model numbers, so it is normal for them to want different update sizes.

5. More regularization helped

Raising WEIGHT_DECAY to 0.3 improved validation score. In plain English, it added a stronger “do not memorize too wildly” pressure while the model learned.

Glossary

Model The architecture plus the learned numbers inside it.
Architecture The model's structure: layers, width, attention blocks, embeddings, and output head.
Parameter A learned number inside the model. Training changes these numbers.
Hyperparameter A setting chosen by us before training, such as depth, learning rate, or batch size.
Learning rate How large each training update is. Too low learns slowly; too high can overshoot.
Batch size How many tokens are used before one optimizer update.
Optimizer The algorithm that updates model parameters based on training error.
Embedding The learned numeric representation of a token.
Unembedding / output head The layer that turns the model's internal state into next-token predictions.
Weight decay A regularization setting that discourages weights from growing too freely.
Validation Testing the trained model on held-back text it did not train on directly.
val_bpb Validation bits per byte. This run's score. Lower is better.
Generated from results.tsv and the current best train.py settings on the autoresearch/may20-folktales branch.
